## 二、基于真实工程事实的架构决策（已验证依据，ZCode 可直接执行）

### ADR-001｜`Order` 领域类置于 `com.dji.sale` 包，`SerialNumberGenerator` 置于 `com.dji.product` 包
- **状态**：已定（基于真实源码强约束）
- **依据**：
  1. 教师既有 `com.dji.promotion.DJIPromotion` 第 5 行写死 `import com.dji.sale.Order;`；
  2. 教师既有 `com.dji.product.DJIProductDemo` 共 10 处调用同包下 `SerialNumberGenerator.getInstance().nextSerialNumber()`。
- **决定**：在 `com.dji.sale` 包定义 `Order` 及其值对象/枚举，在 `com.dji.product` 包定义 `SerialNumberGenerator`，实现对教师既有源码**零破坏性修改**并立即恢复编译。

### ADR-002｜地区枚举与产品型号严格对齐真实 `order.json` 与 `DJIFactory`
- **状态**：已定（基于阶段 0 数据勘察事实）
- **依据**：
  1. `order.json` 中亚太地区字段值为 `"ASIA"`（`sysgui.png` 中文显示“亚太”），其余为 `CHINA_MAINLAND`、`NORTH_AMERICA`、`EUROPE`、`SOUTH_AMERICA`；
  2. `order.json` 与 `DJIFactory` 常量中的消费级型号为 `"Mini 4 PRO"`、`"Air 3S"`，而非任务书正文表格示例的 `"Mini 4"`、`"Air 3"`，且任务书明文规定“以实际 JSON 中的产品型号为准”。
- **决定**：`Region.ASIA` 映射 JSON `"ASIA"` 与中文显示名“亚太”，路由至日本名古屋工厂；型号校验以 `DJIFactory` / `DJIProductDemo` 9 个精确型号为准。

### ADR-003｜客户名 `U+200C` 零宽字符清洗与原值保留策略
- **状态**：提议（默认启用，作为任务 8“经测试发现并修正的问题”核心案例）
- **依据**：ZCode 勘察实证 `order.json` 中订单 `2025102900009` 客户名为 `\u200cElizabeth Taylor`（首字符 `U+200C`）、`2025102900010` 为 `Emil\u200c`（尾字符 `U+200C`），且 `sysgui.png` 中显示无不可见字符。若不清洗，用户输入 `Emil` 或 `Elizabeth` 精确/前缀匹配及按客户统计分组会出现失配。
- **决定**：`Customer` 同时保存 `rawName`（原始 JSON 值）和 `normalizedName`（剥离 Unicode 格式控制字符 `\p{Cf}` 并 `trim()`）。界面展示与关键字查询统一使用 `normalizedName`。

### ADR-004｜促销策略接口双层设计（兼容 `DJIPromotion` + 结构化 `PromotionStrategy`）
- **状态**：已定
- **依据**：教师接口 `DJIPromotion#calculatePromotion(Order)` 仅返回 `BigDecimal`（减免额），而任务 5 要求“返回结构化结果，至少包含活动名称、优惠金额、应付金额”。
- **决定**：定义 `PromotionStrategy extends DJIPromotion`，新增 `PromotionResult evaluate(Order)`，并在接口默认方法中令 `calculatePromotion(Order)` 返回 `evaluate(order).getDiscountAmount()`，兼顾教师接口兼容性与任务 5 结构化要求。

### ADR-005｜`BigDecimal` 小数位与舍入规则统一为 `scale=2, RoundingMode.HALF_UP`
- **状态**：已定（已由 `sysgui.png` 14 笔期望值反证核实）
- **依据**：`sysgui.png` 中全部 14 笔订单（含 `CNY`、`USD`、`EUR`、`JPY`、`BRL`）均保留两位小数（如 `0001` 优惠 `2550.24`、应付 `11617.76`；`0012` `JPY 697800.00`）。
- **决定**：所有币种金额展示与折扣乘法结果统一使用 `setScale(2, RoundingMode.HALF_UP)`。

### 实施启动时用户追加的三项架构修正（本阶段必须落实）

1. **序列号创建入口**：业务调用方不得通过公开注册表接口指定序列号；`DroneSpecRegistry` 对业务侧只暴露 `createDrone(productType)`，序列号由注册表内部向 `SerialNumberGenerator` 统一申请。教师既有产品构造器仍公开接受 `sn` 参数（保持教师 API 兼容），该封装限制在设计说明中披露。
2. **生产中途失败**：除路由前置校验外，必须处理产品创建/生产流程中途异常——部分成功不得误报整单成功；已消耗序列号不回收倒退；记录失败原因与实际完成明细；重复操作语义安全（重试只补产未完成明细）。
3. **统计口径**：区分"预计基地需求量"（订单明细静态汇总）与"实际生产成功量"（已完成生产任务汇总）；未执行生产时不得将预计量呈现为已产量。

### 实施备注｜PromotionType 归属包更正

蓝图 §6.1 将 `PromotionType` 草图在 `com.dji.promotion`，但其领域结果对象 `PromotionResult` 按计划置于 `com.dji.sale`。为遵守依赖硬约束"SALE 严禁反向依赖 PROMO（保持单向 PROMO→SALE）"，`PromotionType` 实际落在 **`com.dji.sale`** 包（领域枚举），`com.dji.promotion` 引用之。此为依赖方向约束下的必要放置更正，不改变任何业务语义。
